# NewAPI 会话刷新防泄漏设计

## 目标

修复 UpstreamOps 监控 NewAPI 渠道时因刷新请求不符合新版同源校验、刷新并发和无条件重新登录而持续创建上游登录会话的问题。修复后，正常监控只轮换已有会话的刷新令牌，不会按扫描周期创建新的登录会话；临时上游故障也不会触发登录风暴。

## 根因

新版 NewAPI 在安全 Cookie 模式下通过 `SessionCookieOriginGuard` 保护 `/api/user/auth/refresh`，要求请求携带与目标站点同源的 `Origin` 或 `Referer`。当前 NewAPI connector 只发送刷新 Cookie，因此刷新会返回 `403 AUTH_ORIGIN_FORBIDDEN`。

渠道服务把任意刷新错误都解释为“刷新令牌不可恢复”，随后立即调用密码登录。每次密码登录都会在 NewAPI 创建新的长期活动会话，旧会话没有被撤销。定时扫描持续运行后，上游会依次触发活动会话上限 `409 AUTH_SESSION_LIMIT` 和创建频率限制 `429 AUTH_SESSION_ISSUANCE_LIMIT`。

同一渠道还可能被余额扫描、倍率扫描和手动操作同时访问。当前 `EnsureSession` 没有按渠道串行化，两个调用可能读取同一枚一次性刷新令牌并竞争轮换，进一步触发错误回退。

## 设计

### 同源刷新请求

`backend/connector/newapi` 从渠道 `site_url` 解析 `scheme://host`，作为刷新请求的 `Origin`。URL 中的路径、查询和尾斜杠不进入 Origin。无法解析出 HTTP/HTTPS Origin 时直接返回输入错误，不发送刷新请求。

登录和普通 Bearer API 请求保持现状。此次不伪造全局 Resty Header，避免影响其它上游接口。

### 刷新错误策略

connector 层增加可被 `errors.As` 识别的刷新错误元数据，用于表达该错误是否允许密码登录回退。未携带元数据的旧 connector 错误保持现有行为，以免改变 Sub2API 语义。

NewAPI 的策略如下：

- `401`，且表示刷新会话已经失效或撤销：允许回退密码登录。
- `403`、`409`、`429`、5xx、网络错误、超时、响应解码错误或协议字段缺失：不允许回退登录。
- 不允许回退的错误原样返回给监控任务，并保留本地缓存会话，供下一次扫描重试。

这个策略优先保护上游账号的会话额度。真正失效的会话仍可自动恢复；临时或协议错误不会通过创建新会话来掩盖。

### 按渠道串行化

`channel.Service` 为每个渠道维护一把进程内互斥锁。`EnsureSession` 的读取、校验、刷新、登录和持久化全过程在该渠道锁内完成；不同渠道仍可并发扫描。

第二个等待者拿到锁后重新读取数据库，因此会复用第一个调用刚写入的轮换后令牌，不会重放旧刷新令牌。锁只保护单进程部署的当前架构，不新增数据库锁或分布式依赖。

### 删除与清理

此次不增加远程注销：删除渠道时可能已无法刷新会话，远程注销还需要扩展 connector 协议并定义失败时是否阻止删除。当前修复保证不再产生新泄漏；既有上游会话仍通过 NewAPI 的“退出其他会话”或密码重置清理。

## 测试

- NewAPI connector 测试刷新请求携带正确的 `Origin`，并覆盖带路径的 `site_url`。
- 测试非法站点 URL 在发送请求前失败。
- 测试 401 被标记为允许重新登录；403、409、429、5xx、网络和协议错误被标记为禁止重新登录。
- 渠道服务测试禁止回退的刷新错误不会调用登录，也不会删除已保存会话。
- 渠道服务测试明确失效的刷新错误只执行一次登录并保存新会话。
- 并发测试让两个 `EnsureSession` 同时请求同一渠道，断言只发生一次刷新，另一个调用复用刷新结果。
- 运行 `go test ./backend/connector/newapi ./backend/channel`，随后运行 `go test ./...` 和 `go vet ./...`。

## 非目标

- 不修改 NewAPI 服务端的会话上限或安全校验。
- 不自动重置上游账号密码或清理已有会话。
- 不修改数据库结构、前端或定时任务频率。
- 不引入跨进程分布式锁；当前部署是单进程，进程内按渠道锁与现有架构一致。
